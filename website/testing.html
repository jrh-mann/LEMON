Testing

Testing Strategy

We test LEMON at several levels: unit tests for individual functions, integration tests for module interactions, end-to-end browser tests, a custom evaluation framework for measuring LLM quality, and user acceptance testing with our project partners.

Layer Tool Approximate Count Purpose
Unit pytest [1] 46 test files Verify individual functions and modules
Integration pytest [1] 47 test files (integration + features) Verify cross-module interactions
Frontend Unit Vitest [4] 4 test files Verify frontend stores and utility functions

Altogether the backend test suite has over 1,300 automated tests across 93 test files.

Unit Testing

Why

Unit tests catch regressions when we change individual components. Each backend module (parser, evaluator, tools, validation, workflow storage) has its own test file that verifies it works correctly on its own.

Tool

pytest [1], the standard Python testing framework. Tests are organized by module in the tests/ directory.

How Tests Are Conducted

Tests are organized into subdirectories by functionality. Each test file focuses on a single module or feature. Tests use pytest fixtures for setup and run without any external dependencies (no API calls, no database servers).

Results

Test Area Files What's Covered
Execution 15 Expression parser tokenization, AST construction, evaluator operators, type coercion, TreeInterpreter workflow walking
Tools 7 add_node, modify_node, delete_node, connections, batch edit, variable management
Validation 8 Structural rules, edge cases, start node constraints, reachability, branch completeness
Workflow 14 CRUD operations, persistence, library management, save/load contract
Evaluation 2 Scorer dimensions, functional scoring, threshold extraction

Analysis

The heaviest test coverage is on the execution engine (parser, evaluator, interpreter) and the tool system, which are the core components that must be correct for workflows to function. The execution tests alone cover tokenization of condition strings, AST construction for compound expressions, evaluation with type coercion, and full workflow traversal including subworkflow recursion.

Integration Testing

Why

Individual modules can pass their own tests while breaking when combined. Integration tests catch these problems.

Tool

pytest [1], using the same framework as unit tests but with fixtures that set up multi-component environments.

How Tests Are Conducted

Tests in tests/integration/ and tests/features/ set up scenarios involving multiple backend components. These cover event bus communication between the orchestrator and the frontend transport layer, database schema migration sequences from version 0 through 8, workflow save-load cycles ensuring data integrity, and API route handling with authentication middleware.

Results

Test Area Files What's Covered
Features 24 Feature-level integration (subworkflows, export, cancellation, streaming)
Integration 23 Event bus, schema migrations, API routes with auth, cross-module flows

47 test files in total. All tests are automated and run locally via pytest.

Analysis

These tests were especially useful during the Socket.IO to SSE migration. The existing suite caught several regressions where the new SSE layer didn't propagate tool events the same way Socket.IO had.

End-to-End Testing

Why

Some bugs only show up when you run the full stack. E2E tests catch these by automating real browser interactions against a running backend.

Tool

Playwright [2], a browser automation framework. Tests run in a real browser against a real backend (not mocked).

How Tests Are Conducted

Test specs in src/frontend/tests/e2e/ automate user interactions: typing in the chat panel, waiting for LLM responses, verifying canvas updates, checking modal dialogs, and testing navigation flows.

Results

Twelve test spec files covering core user journeys:

Analysis

Running against a real backend (no mocks) means the tests reflect what users actually experience. The downside is slower execution and needing an API key, but the extra confidence is worth it.

Prompt Testing

Why

Normal unit tests don't work well for LLM output because the results aren't deterministic. When we change a prompt or update the model, we need to know whether extraction quality went up or down. That's what the evaluation framework is for.

Tool

Custom evaluation framework built in eval/. Uses pytest-compatible test infrastructure.

How Tests Are Conducted

Benchmark tasks with reference (golden) workflows. The evaluation harness runs the orchestrator against a natural language description, then scores the extracted workflow against the golden reference across six dimensions: variables, nodes, topology, conditions, outputs, and functional routing agreement [3]. See the Algorithms page for detailed scoring methodology.

Results

The framework currently evaluates against diabetes treatment and liver pathology benchmark workflows. Scoring runs across multiple models and configurations to detect regressions.

Analysis

This gives us actual numbers instead of just "it seems to work". When we change a prompt or tool schema, we can run the eval suite and see exactly which dimensions got better or worse.

User Acceptance Testing

Why

Passing tests doesn't mean the system is actually useful. We needed people with different backgrounds to sit down with LEMON and tell us what worked and what didn't: a doctor for clinical correctness, a technical advisor for robustness, and a classmate for a fresh pair of eyes on the UI.

Participants

Tester Background Focus
Dr Valeed Medical doctor Clinical accuracy: do the workflows reflect how decisions are actually made?
Haider Khokhar Project partner (Trigger Point Labs), medicine and technology Both: does the system handle real clinical pathways and is the implementation solid?
Luca Philosophy student, no prior exposure to LEMON UI/UX: can someone pick this up and use it without being told how?

How Tests Were Conducted

All sessions were in person. We sat with Dr Valeed and Haider together and demo'd the system, then let them drive. Luca tested separately with minimal instruction so we could see where he'd get stuck on his own. In each case we watched what they did, wrote down where they paused or got confused, and asked follow-up questions at the end.

Test Scenarios

ID Scenario Task What we wanted to learn
UAT-1 Chat-driven workflow creation Describe a clinical workflow in plain language and have the system build it Does the orchestrator understand how clinicians actually talk about their processes?
UAT-2 Reviewing and editing Look at the generated workflow and fix anything that's wrong, using chat or the canvas Can users read the visual output and correct it without help?
UAT-3 Decision logic Check branching conditions on a workflow with thresholds (e.g. lab value cutoffs) Are the branch conditions clinically right, and can the tester tell?
UAT-4 Stepped execution Run a workflow step-by-step, enter inputs, follow the highlighted path Is the execution trace clear enough to catch logic errors?
UAT-5 Export Export as Python and as a PNG Are the exports actually useful outside of LEMON?
UAT-6 Cold start Use the system from scratch with no guidance How far does someone get before they need help?

Results and Feedback

Dr Valeed

Dr Valeed's main point was about priorities. He felt we should be spending our time getting the core workflow logic right, making sure decisions branch correctly and the execution engine handles real clinical pathways, rather than adding extra features or polishing the interface. From his perspective, a tool like this is only useful if the underlying logic is trustworthy. A nicer UI doesn't matter much if a decision node sends a patient down the wrong path. This pushed us to put more time into the execution engine and validation layer in the final stretch of the project.

Luca

Luca had no trouble with the chat side of things. Typing a description and watching the workflow appear on the canvas made sense to him straight away, and the stepped execution view where nodes light up as they run was easy for him to follow. The parts that tripped him up were more on the manual editing side. Connecting nodes by dragging between ports wasn't obvious until we pointed it out, and some of the terminology in the right sidebar (things like "subprocess" and "calculated" as variable sources) didn't mean much to him. He also wasn't sure what the difference between the node types was at first, or why a decision is a diamond and a calculation is a rectangle. None of this stopped him from using the system through chat, but it would have been a barrier if he'd tried to build a workflow entirely by hand.

Analysis

The two perspectives gave us quite different things to work on. Dr Valeed cared about substance: get the decision logic right before worrying about anything else. Luca cared about surface: the chat path worked well, but the manual editing tools assumed knowledge he didn't have. Both were fair, and they pointed in the same direction. The AI-assisted path was the stronger experience, and that's where our effort was best spent.

In terms of what actually changed: in early February we overhauled decision node edge labels so that true/false branches are enforced and auto-assigned, and fixed a bug where empty labels caused the wrong branch to be taken. In late February we redesigned the layout with a tabbed navigation structure and improved canvas interactions. Through early March we simplified compound condition labels (replacing verbose AND/OR with & and |, and using "Else" instead of negating every condition), thickened connection arrows for visibility, and added inline reasoning so users can see why the AI made the choices it did. Not all of this was directly prompted by the UAT sessions, but the feedback confirmed we were fixing the right things.

The main takeaway was that the chat interface is the real onboarding mechanism. Luca, with no technical background, could describe what he wanted and get a working workflow. The visual editor is there for refinement, but the way in is the conversation, not the canvas. That's worth knowing if the project were to continue.
