Related Projects

Camunda [1]

Camunda is an open-source BPMN workflow engine for business process automation. It offers visual modeling, execution, and monitoring of process flows, and is widely used in enterprise settings. Features include a graphical BPMN designer, a REST API for deployment, and detailed execution history. The main drawback for our use case is that Camunda expects users to understand BPMN notation and XML. The takeaway for LEMON was that workflow tools for clinicians need to work without any specialized notation. Our chat-based interface lets users describe what they want in plain language instead.

OpenCDS [2]

OpenCDS is an open-source clinical decision support framework built around HL7 and FHIR standards. It integrates with electronic health record systems and supports standards-compliant rule execution via CDS Hooks and CQL. The framework is powerful but heavy: it takes a lot of setup and configuration to get running, and it assumes deep integration with existing hospital IT. For LEMON, the lesson was that we should focus on the authoring side of the problem. Rather than trying to plug into live clinical systems, LEMON creates and validates workflows, then exports them in formats that downstream systems can consume.

LangChain / LangGraph [3]

LangChain and LangGraph are general-purpose LLM agent frameworks. LangChain chains LLM calls with retrieval, memory, and external tools; LangGraph adds a graph-based model for stateful agent workflows. They are flexible but not domain-specific. We considered using LangChain as a base but decided against it because we needed tight control over how tool calls map to validated workflow operations. LEMON implements its own orchestration loop where every tool call directly modifies the workflow graph and is validated on each step. A generic agent framework would have added abstraction without giving us the domain-specific constraints we needed.

Technology Review

LLM Provider

Option Pros Cons Our Choice
Claude (Anthropic) Native tool use API, extended thinking mode, streaming support, strong instruction following Higher per-token cost Yes
GPT-4 (OpenAI) Mature ecosystem, function calling support, wide adoption Less native tool-use integration than Claude at the time of evaluation
Gemini (Google) Competitive performance, long context window Less mature tool-use API when evaluated

We initially prototyped with an OpenAI-based approach but switched to Claude in January 2026 after finding its native tool use API [4] more reliable for our use case. Our orchestrator needs the LLM to return precise, structured tool calls (not free-form text), and Claude's tool use was the most consistent option we tested for generating valid node operations.

Backend Framework

Option Pros Cons Our Choice
FastAPI Async-native, automatic OpenAPI docs, Pydantic validation, SSE streaming support via StreamingResponse Yes
Flask Simple and flexible, large ecosystem No native async support, SSE requires extensions
Django Full-featured with ORM, admin panel, authentication Heavyweight for an API-focused project

We started with Flask [5] for the initial prototype because of its simplicity, but migrated to FastAPI in March 2026. As the project grew, we needed native async support and SSE streaming, which Flask could not provide without heavy extensions. FastAPI's Pydantic integration also saved us a lot of manual request validation, and the auto-generated OpenAPI docs were useful during development.

Frontend Framework

Option Pros Cons Our Choice
React Large ecosystem, component model, hooks for state management, team familiarity Yes
Vue Simpler learning curve, good documentation Smaller ecosystem for complex canvas-based UIs
Svelte Compiled approach, minimal runtime Less community support for SVG-heavy canvas applications

Most of the team already knew React, and Zustand gave us a lightweight way to manage the complex canvas state [6]. The workflow editor does a lot of SVG manipulation, and React's ecosystem had better support for that than the alternatives.

Real-time Communication

Option Pros Cons Our Choice
Server-Sent Events (SSE) Simple unidirectional server-to-client streaming over HTTP, no protocol upgrade needed, works with HTTP/2 Yes
WebSocket (Socket.IO) Bidirectional communication, automatic reconnection Requires protocol upgrade, more complex server infrastructure
Polling Simple to implement Higher latency, unnecessary server load

We started with Socket.IO but realised partway through development that we only actually needed server-to-client streaming (LLM responses, tool call updates, execution events). We never used the client-to-server channel that WebSockets provide. We migrated to SSE in March 2026, which simplified the infrastructure considerably [7].

Database

Option Pros Cons Our Choice
SQLite Single-file, zero-configuration, no separate server process, sufficient for per-user workflow storage Yes
PostgreSQL Full-featured relational database, concurrent access, scalability Overhead not justified for a single-instance deployment

Our data is mostly workflow definitions, user accounts, and conversation logs. These are small, per-user datasets, so a full database server would have been overkill. SQLite's zero-config, single-file approach kept deployment simple [8], which was especially helpful on Azure where we didn't want to manage a separate database instance.

State Management

Option Pros Cons Our Choice
Zustand Minimal API, no boilerplate, works well with React hooks Yes
Redux Industry standard, powerful middleware Verbose for a project of this scale
Context API Built into React, no dependencies Does not scale well for complex state with frequent updates

Zustand was the obvious pick for state management [9]. The canvas state updates constantly as nodes get added, moved, and connected, and Zustand handles that without the boilerplate that Redux would have required.
