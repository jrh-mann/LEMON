Implementation

This section describes the implementation of LEMON's key features. Each subsection covers what the feature does, how it was built, which libraries and frameworks were used, and includes a short code snippet where helpful.

LLM Orchestrator and Tool Use

The orchestrator manages a multi-turn conversation with Claude where each turn may involve multiple tool calls that modify the workflow. The Orchestrator class maintains workflow state, conversation history, and a ToolRegistry containing over 20 tools. Each turn sends the conversation to Claude with available tool schemas. Claude responds with tool calls (e.g. add_node, add_connection, modify_node) which are executed against the workflow state. Results are fed back until Claude responds with text. A maximum of 50 iterations prevents runaway loops.

Libraries: Anthropic SDK for Claude API calls, Pydantic for tool parameter validation.

# Simplified main loop from orchestrator.py
def run_turn(self, user_message):
    self.conversation.add_user_message(user_message)
    for _ in range(_MAX_TOOL_ITERATIONS):
        response = call_llm(
            self.conversation.messages,
            self.tools.schemas
        )
        if response.has_text_only:
            return response.text
        for tool_call in response.tool_calls:
            result = self.tools.execute(tool_call, self.workflow)
            self.event_bus.emit("TOOL_COMPLETED", result)
            self.conversation.add_tool_result(tool_call.id, result)

Real-time Streaming (SSE)

All LLM responses, tool call updates, and workflow changes stream to the frontend in real time using Server-Sent Events. The EventSink class is a thread-safe queue. The ChatTask (running in a background thread) pushes events as the orchestrator executes tools. The FastAPI endpoint yields these events as SSE-formatted strings via StreamingResponse. The frontend's EventSource API receives events and updates Zustand stores, which trigger React re-renders.

The project originally used Socket.IO for real-time communication but migrated to SSE in March 2026. The system only needs server-to-client streaming, so SSE was simpler and eliminated the need for a WebSocket protocol upgrade.

Libraries: FastAPI StreamingResponse, native browser EventSource API.

# EventSink from sse.py
class EventSink:
    def __init__(self):
        self._queue = queue.Queue()
        self._closed = False

    def push(self, event, data):
        if not self._closed:
            self._queue.put((event, data))

    def __iter__(self):
        while True:
            item = self._queue.get(timeout=15)  # keepalive
            if item is None:
                break
            event, data = item
            yield f"event: {event}\ndata: {json.dumps(data)}\n\n"

Visual Canvas

The canvas is an interactive SVG surface where workflow nodes are rendered as colored shapes and edges as paths, with drag-and-drop, pan, zoom, and auto-layout. The Canvas component renders the workflow as SVG elements inside a React component. Each node type has a distinct color and shape. Edges are calculated using path routing algorithms. Users can drag nodes (with collision detection), draw connections between nodes, and use keyboard shortcuts for undo/redo. The auto-layout algorithm arranges nodes in a hierarchical tree structure. All canvas state lives in a Zustand store that reacts to both user interactions and SSE events from the backend.

Libraries: React 19 for rendering, Zustand for state management, custom SVG utilities for layout, collision detection, and edge routing.

The canvas rendering logic is spread across several utility modules (layout.ts, collision.ts, edges.ts, geometry.ts) that handle the spatial calculations, while Canvas.tsx coordinates the React rendering and event handling.

Expression Parser and Evaluator

Decision nodes contain conditions like Age >= 65 AND BMI < 30. LEMON includes a custom parser and evaluator that processes these at runtime. The pipeline has three stages. First, the tokenizer scans the condition string into typed tokens (identifiers, numbers, comparators, logical operators). Second, a recursive descent parser builds an Abstract Syntax Tree of BinaryOp, Variable, and Literal nodes. Third, the evaluator walks the AST with a variable context, performing type-appropriate comparisons and returning a boolean result.

Libraries: Pure Python with no external dependencies.

Subworkflows

Subprocess nodes call other workflows, passing inputs and receiving outputs as derived variables. This allows complex workflows to be decomposed into reusable pieces. When the TreeInterpreter encounters a subprocess node, it loads the referenced workflow from the database, maps the parent's variables to the child's inputs, and executes the child workflow recursively. The child's output becomes a derived variable in the parent's context. A build-depth limit prevents infinite recursion. During authoring, subworkflows are built by independent BuilderTask instances that run their own orchestrator conversation in a background thread.

Libraries: FastAPI background tasks, SQLite for workflow storage.

Subworkflow execution follows a recursive pattern: the interpreter calls itself with the child workflow and mapped inputs, then injects the result back into the parent context. Depth limiting (default 2 levels) prevents infinite recursion from circular references.

Image-to-Workflow

Users can upload a flowchart image or PDF, and the system reconstructs it as an editable workflow on the canvas. When a user uploads an image, the backend processes it using Pillow to detect the MIME type from magic bytes (not the file extension, for security). The image is then included in the conversation as a content block using Claude's Vision API. The orchestrator analyzes the image, identifies nodes, connections, conditions, and labels, then uses its workflow tools to reconstruct the flowchart as a structured workflow. This process uses the same tool-use loop as text-based workflow creation.

Libraries: Pillow for image format detection and processing, Anthropic Vision API for image understanding.

Authentication

Session-based authentication with secure password storage. User passwords are hashed using PBKDF2 with a random salt before storage. On login, the submitted password is hashed and compared. A session token (random hex string) is generated and stored in the auth database with an expiration timestamp. The session token is sent to the client and included in subsequent requests as a header. FastAPI middleware validates the session on each request. Rate limiting (via slowapi) on the registration and login endpoints prevents brute-force attacks.

Libraries: hashlib (PBKDF2), secrets (token generation), slowapi (rate limiting).

Workflow Persistence

Workflows are stored as JSON in SQLite with schema versioning for safe upgrades. The WorkflowStore class handles all database operations. Workflow data (nodes, edges, variables, outputs, tree representation) is serialized as JSON and stored alongside scalar metadata (name, description, domain, flags). The save contract ensures that nodes, edges, variables, outputs, and the tree representation stay synchronized after every save or update operation.

The database schema uses version-based migrations. Each migration adds columns or tables needed for new features. The current schema is at version 8, having evolved from the initial version to support drafts, publication, build history, conversation linking, and uploaded file tracking.

Libraries: sqlite3 (standard library), json for serialization.
