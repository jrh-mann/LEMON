Implementation

This section walks through how we built LEMON's main features, what libraries we used, and how the pieces fit together.

LLM Orchestrator and Tool Use

The orchestrator runs a loop: send the conversation to Claude along with the available tools, get back tool calls (like add_node or add_connection), execute them against the workflow, and feed the results back. This repeats until Claude responds with plain text instead of tool calls, or we hit the 50-iteration safety limit. The Orchestrator class keeps track of the workflow state, conversation history, and the registered tool set.

Libraries: Anthropic SDK [1] for Claude API calls. Tool inputs are described in a custom ToolRegistry that generates native Anthropic-compatible JSON schemas from per-tool metadata [2].

# Simplified main loop from orchestrator.py
def run_turn(self, user_message):
    self.conversation.add_user_message(user_message)
    for _ in range(_MAX_TOOL_ITERATIONS):
        response = call_llm(
            self.conversation.messages,
            self.tools.schemas
        )
        if response.has_text_only:
            return response.text
        for tool_call in response.tool_calls:
            result = self.tools.execute(tool_call, self.workflow)
            self.event_bus.emit("TOOL_COMPLETED", result)
            self.conversation.add_tool_result(tool_call.id, result)

Developer Tooling

The same ToolRegistry that powers Claude's tool-use loop also supports internal developer tooling. LEMON exposes endpoints that list the registered tools and their generated schemas, and can execute an individual tool directly without running a full chat turn.

This was useful during development because we could inspect schema drift, verify that a new tool had been registered correctly, and reproduce tool-level bugs in isolation before involving the orchestrator, SSE layer, or frontend.

Real-time Streaming (SSE)

Everything streams to the frontend in real time: LLM text, tool call updates, workflow changes, and stepped execution events. The EventSink is a thread-safe queue that background tasks push events into as the orchestrator works. The FastAPI endpoint pulls from this queue and yields SSE-formatted strings via StreamingResponse.

On the frontend, we do not use the browser's EventSource API. Instead, the client opens the stream with fetch() and reads the response body as a ReadableStream. That lets chat and execution streams stay POST-based, carry JSON payloads and cookies, and be cancelled with AbortController while still using the standard SSE wire format.

We originally used Socket.IO but switched to SSE in March 2026 after realising we only ever stream server-to-client. SSE is simpler and doesn't need a WebSocket protocol upgrade.

Libraries: FastAPI StreamingResponse [3], Fetch API and browser stream primitives [4].

# EventSink from sse.py
class EventSink:
    def __init__(self):
        self._queue = queue.Queue()
        self._closed = False

    def push(self, event, data):
        if not self._closed:
            self._queue.put((event, data))

    def __iter__(self):
        while True:
            item = self._queue.get(timeout=15)  # keepalive
            if item is None:
                break
            event, data = item
            yield f"event: {event}\ndata: {json.dumps(data)}\n\n"

Visual Canvas

The canvas renders workflow nodes as coloured SVG shapes and edges as routed paths. Users can drag nodes (collision detection stops them overlapping), draw connections between ports, pan and zoom, and use keyboard shortcuts for undo/redo. There's also an auto-layout button that arranges everything into a hierarchical tree. All canvas state lives in a Zustand store that updates from both user interactions and SSE events coming from the backend.

Libraries: React 19 [5] for rendering, Zustand [6] for state management, custom SVG utilities for layout, collision detection, and edge routing.

The canvas rendering logic is spread across several utility modules (layout.ts, collision.ts, edges.ts, geometry.ts) that handle the spatial calculations, while Canvas.tsx coordinates the React rendering and event handling.

Expression Parser and Evaluator

Decision nodes have conditions like Age >= 65 AND BMI < 30 that need to be evaluated at runtime. We built a custom parser for this. It works in three stages: first, a tokenizer splits the string into typed tokens (identifiers, numbers, comparators, AND/OR). Then a recursive descent parser turns those tokens into an AST. Finally, an evaluator walks the tree with the current variable values and returns true or false.

Libraries: Pure Python with no external dependencies.

# Token types from parser.py
class TokenType(Enum):

    GTE = "GTE"                # >=
    LTE = "LTE"                # <=
    EQ = "EQ"                  # ==
    NEQ = "NEQ"                # !=
    GT = "GT"                  # >

Subworkflows

Subprocess nodes let you call one workflow from inside another, passing in variables and getting a result back. This is how we handle complex clinical logic: break it into smaller, reusable pieces. When the TreeInterpreter hits a subprocess node, it loads the child workflow from the database, maps the parent's variables to the child's inputs, and runs it recursively. A depth limit stops circular references from causing infinite recursion.

During authoring, long-running parent and child builds are handled by dedicated daemon threads (ChatTask and BuilderTask) rather than request-scoped FastAPI background tasks, so the HTTP layer can return a streaming response immediately while the build continues in the background.

Subworkflow execution follows a recursive pattern: the interpreter calls itself with the child workflow and mapped inputs, then injects the result back into the parent context. Depth limiting prevents infinite recursion from circular references.

Runtime support: Python threading [12], SQLite [11] for workflow storage.

Upload Pipeline and Image-to-Workflow

Users can upload flowchart images or PDFs and have them reconstructed as editable workflows. Uploaded files are stored in managed server-side storage, linked back to the current workflow, and reused when the session is resumed or the page is refreshed.

The upload pipeline is deliberately stricter than a normal file picker flow. The backend decodes the incoming file, detects the real type from the payload rather than trusting the filename, saves it under a controlled uploads directory, and only then passes the content into the image-analysis path. That reduces the risk of malformed or mislabeled files entering the workflow reconstruction pipeline.

Once a file is accepted, the orchestrator treats it as another authoring input. Claude's Vision API extracts nodes, connections, and conditions from the uploaded diagram, and the same tool-use loop used for chat authoring rebuilds the workflow on the canvas. In practice this means image/PDF authoring and text authoring converge on the same internal workflow model.

Libraries: Pillow [7] for image format detection and processing, Anthropic Vision API [8] for image understanding.

Authentication

We use session-based auth. Passwords are hashed with PBKDF2 and a random salt. On login, a session token gets generated, hashed, and stored in SQLite with an expiry. The raw token is set in an HTTP-only cookie, and protected FastAPI routes resolve the current user through an auth dependency backed by the session store. We also added rate limiting on the login and registration endpoints to prevent brute-force attacks.

Libraries: hashlib (PBKDF2 [9]), secrets (token generation), slowapi [10] (rate limiting).

Library, Peer Review, and Workflow Packages

The library manages both standalone workflows and multi-workflow packages. A package has one head workflow and zero or more dependency workflows, which keeps reusable subworkflows together for review, transfer, compilation, and cloning. Package membership and head/dependency roles are stored explicitly in the database and exposed through dedicated /api/packages/* routes.

The public review flow is package-first rather than workflow-first. When a user publishes something for peer review, the package becomes the review unit and the head workflow becomes its public entry point. Other users browse published packages, inspect the head workflow, and vote on the package as a whole rather than on disconnected workflows.

This matters because review is tied to reuse. A reviewed package can be cloned into another user's library, keep its internal workflow relationships, and carry along any dependent subflows that the head workflow needs. The package service also supports autofetching referenced subflows so reusable workflow groups stay internally consistent.

Voting still uses a simple net-vote threshold (currently 1) to promote a package from unreviewed to reviewed, but the storage model is richer than a vote counter: package metadata, package membership, public visibility, and vote history are all part of the same subsystem.

Libraries: FastAPI [3] for package and peer review API routes, SQLite [11] for package membership, publishing metadata, and vote storage.

Bundle Import and Export

LEMON supports both simple workflow transfer and bundle-based transfer. A single workflow can be exported as JSON for straightforward interoperability, but bundle import/export exists for cases where one workflow depends on others or where a full package needs to move as a unit.

Bundles preserve more context than plain JSON. They can carry multiple workflows, package membership, head/dependency roles, and warnings about missing subflows so the receiving side knows whether the transfer is complete. This makes reuse and collaboration much safer than exporting one workflow at a time.

On import, the backend validates the payload, remaps workflow IDs, reconstructs package relationships where needed, and reports warnings instead of silently dropping broken references. On export, the frontend can package multi-file artifacts cleanly for the user while the backend remains responsible for the canonical workflow/package data.

Compile-to-Python

Exporting to Python is not just a download format; it is a compilation step that turns the workflow tree into executable code outside LEMON. The backend supports compilation of an in-memory workflow, a stored workflow, or a full package headed by a chosen workflow.

The compiler lowers workflow nodes into a standalone Python function, generates helper functions when needed for shared branches or subprocesses, and follows subworkflow references so package compilation can include dependent workflows as part of the generated output.

Compilation also produces warnings when the source graph is incomplete, for example if a referenced subworkflow cannot be fetched or a recursive dependency is detected. That way the export path stays useful for downstream engineering systems without pretending every workflow can be compiled perfectly.

Workflow Persistence

Workflow data is stored in SQLite. The WorkflowStore class serializes nodes, edges, variables, outputs, and the tree representation as JSON alongside scalar metadata such as name and description. The same database also stores package metadata, package membership, and package votes so workflows and reusable workflow packages stay consistent during save, clone, export, and publish operations.

The schema uses version-based migrations. The current migration set goes up to version 11, reflecting additions over time for drafts, publication, build history, conversation linking, uploaded file tracking, and package tables/metadata.

Libraries: sqlite3 [11] (standard library), json for serialization.
