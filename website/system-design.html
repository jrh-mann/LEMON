System Design

System Architecture

LEMON follows a layered architecture. The React [1] frontend, with Zustand [5] for state management and a library view that handles both workflows and packages, communicates with the FastAPI [2] backend via REST API calls and receives real-time updates through Server-Sent Events [3]. On the client, those SSE responses are consumed with fetch() and stream parsing so chat and execution runs can stay POST-based and abortable. The backend orchestrates Claude API [6] interactions through a tool-use loop, while the same storage layer supports workflow CRUD, package management, peer review, and execution. Workflow execution is handled by a dedicated interpreter that evaluates conditions using a custom expression parser.

Design Patterns

Pattern Where Used Purpose
Observer EventBus (events/bus.py) Decouple tool execution from transport. Subscribers receive TOOL_STARTED, TOOL_COMPLETED events without knowing about SSE [3] or the frontend.
Registry ToolRegistry (tools/core.py) Central catalog of 20+ tools. Generates JSON schemas for the Claude API [6] automatically. New tools are registered declaratively.
Interpreter TreeInterpreter (execution/interpreter.py) + Parser/Evaluator Walk the workflow tree at runtime, evaluate conditions, execute calculations. Classic interpreter pattern for a domain-specific language.
Factory build_orchestrator (agents/orchestrator_factory.py) Create configured Orchestrator instances with the correct tools, event bus, and session context for each chat interaction.

Data Storage

LEMON uses three separate SQLite [4] databases to isolate concerns. Workflow data is kept in workflows.sqlite, authentication data in auth.sqlite, and conversation history in conversation_log.sqlite. The workflow database stores both individual workflows and reusable workflow packages, and its migration system currently runs up to version 11. Bundle Transfer and Compilation

The transfer and compilation endpoints form a small interoperability layer around the workflow engine. Bundle routes preserve workflow/package relationships during import and export, while the compilation routes expose the same underlying workflow graph as executable Python for downstream systems.

Architecturally, this keeps workflow authoring separate from workflow exchange. Users may design a workflow in the editor, but transfer and compilation are handled by dedicated backend services that validate dependencies, preserve package structure, and warn when referenced subflows are missing.

Uploads and Public Review

Uploaded images and PDFs are treated as workflow-linked assets rather than anonymous files. They are saved in managed storage, referenced from the workflow record, and re-served through a backend route so the same upload can support authoring, refresh recovery, and later review.

Public review is package-oriented. The published object is the package, the head workflow is its public entry point, and voting attaches to package metadata rather than to isolated workflows. That matches the way LEMON handles reuse, cloning, and dependent subflows elsewhere in the architecture.

Developer Tooling Endpoints

Two internal endpoints support development work around the tool system. GET /api/tools exposes the currently registered tools together with the schemas sent to Claude, while POST /api/tools/{tool_name}/execute runs one tool directly against supplied input.

Architecturally, these endpoints sit alongside the normal application routes but serve an engineering purpose rather than an end-user one. They make it easier to inspect the backend tool surface, debug tool behavior in isolation, and verify registry changes without depending on a full orchestrator conversation.
