Project Background and Goals

Doctors and other clinicians often know their decision-making processes well but have no way to turn that knowledge into something a computer can run. LEMON is built for these non-technical users: people who understand clinical processes but shouldn't need to write code to formalize them.

  1. Reduce the effort required to formalise expert decision logic.
  2. Provide a safe authoring environment with strong validation before execution or export.
  3. Support review, sharing, and reuse of high-value workflows.
  4. Enable export to formats suitable for downstream engineering systems.

Requirement Gathering

We gathered requirements through regular meetings with CloudSurge throughout the project. These sessions helped us narrow the scope, sort out priorities, and check our technical direction. The outcome was a formal requirements specification document, reviewed and signed off by all stakeholders.

No formal user survey was conducted. Requirements were collected through direct stakeholder meetings and iterative discussion with the project partners.

Meeting 1: Initial Kickoff (17 October 2025)

Attendees: Team 27, Ilyas (CloudSurge)

Mostly exploratory. Ilyas talked about the problem clinicians have formalising their decision-making processes and we discussed a few possible directions: a general-purpose decision engine, a documentation tool, or something more interactive. He was clear that the target users would be clinicians with no programming background, which ruled out anything that required code. We left without firm requirements but with a sense that the project should be about workflow authoring, not large-scale execution.

Meeting 2: Scope Discussion (31 October 2025)

Attendees: Team 27, Ilyas (CloudSurge)

We pitched the idea of using an LLM to help build workflows through a chat interface, and Ilyas was keen on it. We agreed early on that the system would not touch real patient data: authoring and validation only, no connection to EHRs or live datasets. Ilyas brought up image uploads, suggesting clinicians could photograph paper flowcharts and have them converted. We noted it as a stretch goal since we were not sure it was technically feasible yet. JSON and some form of executable export came up as desirable outputs. We agreed to draft an initial requirements list for next time.

Meeting 3: First Requirements Review (14 November 2025)

Attendees: Team 27, Ilyas (CloudSurge)

We presented a short first draft of functional requirements covering basic workflow creation, a visual editor, and export. Ilyas pushed for stronger validation, arguing that in a clinical setting people need to trust that a workflow is structurally sound before relying on it. We had originally proposed just start, process, decision, and end nodes, but he thought calculation nodes and some kind of subprocess support would be needed for realistic scenarios. Natural-language authoring via chat was discussed as important but secondary to the visual editor. We also talked about performance given the reliance on external LLM APIs. We agreed to come back with a proper MoSCoW-prioritised list.

Meeting 4: Technical Direction (28 November 2025)

Attendees: Team 27, Ilyas (CloudSurge), Haider (Trigger Point Labs)

Haider's first meeting. He walked us through real triage scenarios and pointed out that clinical workflows frequently check multiple conditions at once, so we added compound conditions (AND/OR) as a requirement. He also stressed typed variables: if a workflow compares a patient's age against a threshold, the system needs to know age is a number. We discussed how the orchestrator should order its operations (e.g. registering variables before building nodes that use them). On the technical side, we mentioned we were prototyping with OpenAI but finding its tool-call generation inconsistent. No switch yet, but we flagged it.

Meeting 5: Mid-Project Check-in (16 January 2026)

Attendees: Team 27, Ilyas (CloudSurge), Haider (Trigger Point Labs)

We demoed the working prototype: basic authoring, canvas editor, some validation. The orchestrator had around a dozen tools at this point and we showed how the tool-use loop worked in practice. We were streaming tool calls to the frontend in real time using Socket.IO so the canvas updated as the LLM worked. Ilyas asked about the image upload feature from earlier and we showed early results of passing images to the LLM for analysis. Haider suggested a community gallery with peer review, which we noted as a "Should" priority. We also discussed the problems we were having with OpenAI's tool-call generation and said we were evaluating Claude as an alternative. Ilyas asked about stepping through a workflow to trace its execution path, so we agreed to look into stepped execution. We mentioned we had started writing automated tests alongside development and planned to keep building the test suite as we went.

Meeting 6: Subworkflows and Export (6 February 2026)

Attendees: Team 27, Ilyas (CloudSurge), Haider (Trigger Point Labs)

Driven by a complex clinical scenario Haider described that needed multiple smaller workflows composed together. We had already started on subprocess nodes but the discussion clarified that proper input/output mapping between parent and child workflows was essential. Haider asked whether exported Python code would be usable by an engineer integrating it into an existing system; we confirmed it would preserve the decision logic and control flow. A scenario involving potential infinite loops led us to add a max step limit and cycle detection as non-functional requirements. We also raised the idea of building an evaluation framework to measure how well the LLM extracts workflows from descriptions, since we had no good way of knowing whether prompt changes helped or hurt. Both thought it was worth doing.

Meeting 7: Pre-Submission Review (6 March 2026)

Attendees: Team 27, Ilyas (CloudSurge), Haider (Trigger Point Labs)

Final requirements meeting. We walked through the complete system and demoed all major features, including early evaluation framework results. We had recently migrated from Flask and Socket.IO to FastAPI with native WebSocket support, and were planning to move to SSE next. On security, rate limiting and auth were in place and we had just completed a security audit, with further hardening (XSS prevention, ownership enforcement) planned for the following weeks. Both were satisfied with the core authoring and validation. We reviewed the full MoSCoW table together: the community gallery features (publish, browse, vote) were confirmed as "Should" rather than "Must". We discussed the risk of clinicians treating an authored workflow as an approved clinical protocol and agreed to document it in the risk register. The requirements spec was signed off.

Functional Requirements (MoSCoW)

ID Description Priority
FR1-001 The system shall analyse uploaded workflow diagrams and reconstruct them into structured workflows in the editor Must
FR1-002 The visual editor shall support the node types start, process, decision, calculation, subprocess, and end Must
FR1-003 Users shall be able to create and edit workflows through natural-language interaction with the orchestrator Should
FR1-004 Users shall be able to create and manage typed variables with supported types string, number, boolean, date, and enum Must
FR1-005 The orchestrator shall be able to register variables before creating nodes that depend on them Must
FR1-006 Decision nodes shall support type-appropriate comparators and true/false branching during execution Must
FR1-007 Calculation nodes shall support a documented set of mathematical operators and store results as derived variables Must
FR1-008 Users shall be able to create compound conditions combining multiple comparisons using logical AND/OR Must
FR1-009 Users shall be able to create subprocess nodes that call other workflows and map inputs and outputs Must
FR1-010 The orchestrator shall use workflow tools to create, update, inspect, validate, and save workflows Must
FR1-011 The system shall allow users to switch between multiple workflows for editing and review Must
FR1-012 The system shall allow import of workflow JSON into the editor Should
FR1-013 The orchestrator reasons about workflow correctness during creation Must
FR2-001 The system shall validate workflows against a structural rule set before save, export, or execution Must
FR2-002 Validation shall check start node constraints, reachability, edge references, complete decision branching, variable references, subprocess references, and output consistency Must
FR2-003 Users shall be able to execute a workflow against manually entered input values and inspect output, path, and context Must
FR2-004 Preview execution shall support calculations, derived variables, subprocess execution, and cycle protection Must
FR2-005 The system shall expose step-level execution information for visual playback and debugging Should
FR2-006 Users shall be able to pause, resume, and stop stepped execution Should
FR3-001 Users shall be able to export workflows as structured JSON Must
FR3-002 Users shall be able to export workflows as compiled Python code Must
FR3-003 Users shall be able to export the workflow canvas as a PNG image Should
FR3-004 Exported Python shall preserve control flow, decision logic, and calculation logic Must
FR4-001 Users shall be able to save workflows to a personal library Must
FR4-002 Users shall be able to browse saved workflows through a library interface Should
FR4-003 Users shall be able to publish workflows to a community gallery for peer review Should
FR4-004 Users shall be able to browse workflows published by other users Should
FR4-005 Users shall be able to vote on published workflows, with automatic promotion when a vote threshold is reached Should
FR5-001 The chat interface shall stream orchestrator responses incrementally Should
FR5-002 Long-running orchestrator tasks shall support cancellation by the user Must
FR5-003 The system shall preserve conversation state across multiple turns Must
FR5-004 The system should allow a running task to resume after client refresh Should

Risks

ID Description Likelihood Impact Mitigation
R-001 Sensitive patient data entered into workflows Low Very High Limit scope to authoring/preview, no dataset storage, documented safe-use expectations, authenticated access
R-002 LLM misuse or prompt injection Medium High Restrict orchestrator to explicit tools, validation, authenticated sessions, server-side checks
R-003 Incorrectly authored workflows mistaken for approved clinical logic Medium Very High Require validation, preview execution, review flows, downstream human review
R-004 External API cost or latency impacts usability Medium Medium Bounded orchestration, context compaction, local validation/execution
