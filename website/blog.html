Development Blog

This blog tracks our progress on LEMON from the start of term through to submission. Some entries are rougher than others. The early ones are mostly us trying to figure out what we're building; the later ones get more into the weeds.

Getting started and figuring out the problem

October 25 - November 8, 2025

Had our first meeting with Ilyas. He's explaining the core problem: clinicians write their decision workflows as flowcharts on paper or in Word docs, and there's no straightforward way to turn those into something executable. That gap is basically the whole project.

Spending the first couple of weeks on requirements. Ilyas is good at pushing us to think about things we wouldn't have considered on our own, like typed variables in clinical workflows, the need for strict branching logic, and why auditability matters in this space. We also need to think about the non-clinical stuff: auth, data ownership, export formats.

We're doing the HCI coursework at the same time, which is actually helpful because it's making us do personas and use cases properly before writing any code. We've got three personas: a GP digitising her workflows, a clinical researcher reviewing and sharing them, and an IT admin deploying the system. Think these will be useful to come back to.

Research and early experiments

November 9 - November 25, 2025

Mostly reading and comparing things. Looking at Camunda (BPMN workflow engine), OpenCDS (clinical decision support), LangChain, LangGraph. Main thing from Camunda: BPMN is way too complex for non-technical users. OpenCDS is interesting for the clinical standards side but we're going to focus on the authoring experience rather than integration.

Comparing LLM providers. We need the model to call functions that build a workflow (add nodes, draw connections, set conditions), not just spit out text. Claude's tool-use API feels the most natural for this so we're going with Anthropic.

Jeet's got the repo going and is messing around with ground truth workflows. He has this idea of having reference workflows (like a diabetes treatment pathway) to score against. Not sure where it's going yet but it feels like it could be useful down the line.

Also sketching UI ideas. We've got a dark theme pipeline runner thing, a glassmorphism dashboard, a bunch of others. None of them feel right yet but they're helping us converge on the basic layout: canvas right, chat bottom, tools left.

First code

December 9 - December 20, 2025

First real commits. Got the project structure set up and we're trying to get the LLM to generate Python code directly from a workflow description. Not working great. The generated code is hard to visualise and you can't edit it interactively at all.

We're switching to a structured approach instead: the LLM outputs a tree of nodes and edges as JSON, we render that on a canvas, and code generation can happen as a separate export step at the end. Feels like the right call.

James has got a basic React frontend going with a canvas component. No drag-and-drop yet, just rendering nodes at fixed positions. We're figuring out the node types we need: start, process, decision, end. Might need more later.

Jeet, James

Connecting everything together

January 7 - January 14, 2026

Back from break. I've hooked the frontend up to a proper backend and we've switched from OpenAI to Claude. The tool-use API is the reason. Instead of making the LLM output JSON and parsing it ourselves (which was flaky), we just define tools like add_node and add_connection and Claude calls them directly. Way more reliable.

Backend is in Flask for now. Got the first version of image upload working: you can upload a photo of a flowchart and the system has a go at reconstructing it. Results are rough but you can see the potential.

The rough split right now is: me on frontend + tools, Jeet on image analysis + eval, Axel on orchestrator + streaming, Jude on architecture + system prompt. In reality we're all touching everything.

Building the visual editor

January 15 - January 20, 2026

Bit of a sprint this week. 25+ commits on January 15th alone. We now have drag-and-drop, collision detection, a hierarchical auto-layout thing (we're calling it "beautify"), connection drawing, colour-coded node types, orthogonal edge routing, and pan/zoom.

The beautify algorithm took a few tries. First version just spaced everything evenly which looked awful for tree-shaped workflows. Current version finds the root, does a BFS to assign layers, spaces children under parents. Orphans go in a row at the top.

There's a node palette in the left sidebar now so you can click to add blocks manually. Not everything has to go through the chat. Sometimes you just want to drop a node and connect it yourself.

The beautify button has a flower icon with a pulsing glow. Completely unnecessary but it's fun.

James

Expression parser and execution engine

January 21 - January 29, 2026

Hardest couple of weeks so far. Decision nodes need to evaluate conditions like HbA1c >= 48 AND Age > 30, so we've had to build an actual expression parser. Tokenisation, AST with operator precedence, evaluation with variable bindings. It supports numeric comparators, booleans, string matching, dates, enums, compound conditions with AND/OR.

We've also built the TreeInterpreter on top of that. It walks the workflow from the start node, evaluates conditions at decision points, follows the right branch. Tracks the path so we can highlight it on the canvas afterwards. Has cycle detection and a 1000-node visit limit so a broken workflow can't loop forever.

Tool count is at about 20 now. The main ones: add_node, add_connection, modify_node, delete_node, batch_edit_workflow, validate_workflow, execute_workflow, ask_question.

Also cleaning up the variable system. We've had "inputs" and "variables" as separate concepts which is confusing everyone. Unifying it: variables are either "input" (user provides at runtime) or "derived" (computed by calc/subprocess nodes). Derived ones are read-only.

Library, peer review, first deploy

February 2 - February 6, 2026

Got it running on Azure. Took a while to sort out the Oryx build scripts and uvicorn paths but having a live URL to show Ilyas is worth the pain.

Built out the workflow library. You can save workflows, browse them, switch between them. There's also a peer review thing now: publish to a community gallery, other users upvote/downvote, workflows get promoted once they hit a threshold. Set it to 1 net upvote because we've only got a handful of users.

Added three export formats: JSON, Python, PNG. The Python compiler turns the workflow tree into a standalone function with if/else blocks. You can actually run it outside of LEMON, which is the whole point.

Also added calculation nodes. Before this we only had process nodes (just a label) and decisions (branching). Calc nodes let you do things like BMI = weight / (height * height) and the result becomes a variable that downstream nodes can use.

Image analysis overhaul and subworkflows

February 20 - February 27, 2026

Nothing happened between Feb 6 and Feb 23. We had coursework for other modules.

Back now. Redoing the image analysis from scratch. Multi-file upload (several pages of a flowchart as separate images), PDF preview, two-phase pipeline. First phase classifies what you uploaded (flowchart? legend? side notes?), second phase extracts the workflow using Claude's vision.

Also adding annotation dots on images. When the LLM isn't sure about something in the uploaded flowchart, it sticks a dot on the image and asks you about it. This came from watching people upload messy diagrams with legends and side notes that were confusing the model.

On the frontend side, the layout is getting redone. Going from everything on one page to tabs: workflow builder, library, export. Also reworking the right sidebar and adding a proper variable editing modal.

Subworkflow support is going in too. A subprocess node points to another saved workflow. The parent calls the child with mapped inputs and gets the output back as a derived variable. We're capping it at 2 levels deep so you can't get infinite recursion.

The big migration

March 1 - March 9, 2026

Replacing Flask with FastAPI and Socket.IO with Server-Sent Events in the same week. Probably shouldn't be doing both at once but here we are.

The FastAPI swap is six phases in a day (March 4). Dependencies, app factory, routes, entry point, frontend client, cleanup. Running tests after each phase. The fact that we have decent coverage is what's making this not terrifying.

Socket.IO to SSE is simpler than it sounds. We only need server-to-client streaming, not bidirectional. SSE does that natively with less moving parts. Axel is handling most of it and it's going fine because we already have an event bus between the transport and the business logic.

Switching the tool format from OpenAI-style to Anthropic native too. Getting rid of a translation layer we don't need anymore.

On the prompt side, the system prompt is getting broken into composable sections. Before it was one massive string. Now there are sections for the data model, tool rules, execution, image analysis. Much easier to change one thing without breaking something else.

Axel is also rewriting the E2E tests to hit a real backend instead of mocking Socket.IO. Already finding bugs the mocked tests were hiding.

Testing, security, eval framework

March 10 - March 16, 2026

Architecture is stable so we're spending the week hardening things. Rate limiting (60 req/min/IP), CSP headers, XSS prevention, path traversal checks on uploads, ownership enforcement on all endpoints. That last one is overdue: right now if you know a workflow ID you can access it regardless of who owns it. Fixing that.

Moving all the tests into one tests/ directory (they've ended up in about four different places) and we're past 1,300 now. Mix of execution engine tests, tool tests, validation, storage, integration, and Playwright E2E.

The eval framework is finally coming together. Jeet's ground truth workflows from November plus a scoring system across six dimensions:

  1. Variables - right inputs, right types?
  2. Nodes - right count and types?
  3. Topology - edges connecting the right things?
  4. Conditions - right comparators and thresholds?
  5. Outputs - end nodes producing the right values?
  6. Functional - same inputs reach the same end node?

Two benchmarks so far: diabetes treatment and liver pathology. Run it after any prompt change and you can see what gets better and what gets worse.

User testing

March 12 - March 16, 2026

Testing in person with Dr Valeed (doctor), Haider (project partner), and Luca (philosophy student, no CS). Want three different angles: clinical correctness, technical robustness, usability from cold.

Dr Valeed basically says: stop adding features and make sure the logic is right. Fair point. A workflow tool that sends a patient down the wrong branch is worse than useless.

Luca is fine with the chat path. Describes a workflow, watches it appear, understands the execution highlighting. But he's getting stuck on the manual editing. Dragging between ports to connect nodes isn't obvious to him, and sidebar terms like "subprocess" and "calculated" mean nothing. Confirms what we suspected: the chat is the way in for non-technical users, the canvas is for tweaking after.
