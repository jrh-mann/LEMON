Known Bugs

ID Bug Severity Description
BUG-002 Workflow sync state mismatch Medium There is a synchronisation issue between the frontend and the orchestrator's view of a workflow. The frontend may show nodes that the orchestrator does not see, causing the orchestrator to treat the workflow as empty even when the user has added nodes. This can lead to the LLM rebuilding a workflow from scratch rather than editing the existing one.
BUG-003 Subprocess compilation produces placeholder code Medium When exporting a workflow to Python, subprocess nodes that reference unavailable subworkflows are compiled as TODO comments with None placeholders instead of actual function calls. The exported code will run but skip subprocess logic entirely, producing incorrect results without raising an error.
BUG-004 Inputs/variables terminology inconsistency Medium The database layer stores workflow parameters under the field name "inputs", while the frontend, API types, and tool layer use "variables". The interpreter includes a comment acknowledging the mismatch. This does not cause runtime failures but makes the codebase harder to maintain and can confuse contributors.
BUG-005 Generic error messages on workflow load failure Low When a workflow fails to load due to validation or tree-preparation errors, the API returns a generic error message rather than actionable guidance. Users cannot tell whether the problem is a malformed file, a missing field, or something else.
BUG-006 Debug console.log statements in production frontend Low Over 20 console.log calls with the [SSE] prefix remain in streamActions.ts. These were used during development to trace server-sent event handling and should be removed or replaced with a proper logging utility before release.

Critical Evaluation

UI/UX

The real-time canvas gives good visual feedback as workflows are built. The chat interface works well for users who'd rather describe what they want than manually drag nodes around. Large workflows can get cluttered on the canvas, but auto-layout and zoom help. The stepped execution view with path highlighting turned out to be one of the most useful features for catching logic errors.

Functionality

All 24 "Must" requirements were implemented, and all "Should" requirements too. Subworkflows and stepped execution with pause/resume/stop weren't in the original core spec but turned out to be features that our stakeholders valued highly.

Stability

The system returns structured error messages instead of failing silently, which helped a lot during development. Task cancellation works mid-LLM-call, refreshing the page doesn't lose your session, and rate limiting on the auth endpoints stops brute-force attempts.

Efficiency

Prompt caching cuts API costs when users have similar conversations. Execution is bounded with a max step limit and cycle detection so a badly-formed workflow can't run forever. Long conversations are handled by compacting older messages to stay within the context window.

Compatibility

LEMON is a web application that runs in modern browsers (Chrome, Firefox, Safari, Edge). The backend runs on Python 3.10+ and deploys to Azure. No platform-specific dependencies.

Maintainability

The codebase is split cleanly between API routes, business logic, tools, and storage. Over 1,300 automated tests mean we can refactor with confidence. TypeScript on the frontend catches type errors before they reach the browser. The event bus decouples components well enough that we were able to swap the entire transport layer from Socket.IO to SSE without touching the business logic.

Project Management

We worked iteratively with frequent commits (679 total over 3 months). The four of us worked on features in parallel, running tests throughout. The biggest architectural change, swapping Socket.IO for SSE, went smoothly because the test suite caught regressions immediately.

Future Work

Multi-user Real-time Collaboration

Allow multiple users to edit the same workflow simultaneously with conflict resolution and presence indicators.

Additional Node Types

Add loop nodes for iterative logic, parallel execution nodes for concurrent branches, and wait/timer nodes for time-based workflows.

FHIR/HL7 Integration

Connect LEMON with healthcare interoperability standards to import clinical data schemas and export workflows in standard clinical formats.

Expanded Evaluation Framework

Add more clinical workflow benchmarks beyond diabetes and liver pathology. Include workflows from other domains (administrative, operational) to test generalization.

Role-based Access Control

Add team workspaces with role-based permissions, allowing administrators to manage access and reviewers to approve workflows before use.

Offline Execution Mode

Enable local workflow execution without requiring a cloud API, using a lightweight local model or compiled workflow code.
