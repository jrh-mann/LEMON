LLM Orchestrator (Tool-Use Loop)

The core of LEMON is an orchestrator that manages a multi-turn conversation with Claude [1]. In each turn, the orchestrator sends the conversation history and available tools to the LLM. Claude responds with either text (displayed to the user) or tool calls (executed against the workflow state). Tool results are fed back and Claude may issue further calls. This loop continues until Claude responds with text only, or a safety limit is reached (50 iterations maximum).

The orchestrator maintains workflow state (nodes, edges, variables, outputs), conversation history, and session context. A ToolRegistry provides JSON schemas for 30+ tools that the LLM can call, including add_node, add_connection, modify_node, add_workflow_variable, validate_workflow, and save_workflow.

# Simplified orchestrator loop (from orchestrator.py)
class Orchestrator:
    def __init__(self, tools, event_bus):
        self.tools = tools          # ToolRegistry with 30+ tools
        self.workflow = {"nodes": [], "edges": [], "variables": [], "outputs": []}
        self.conversation = ConversationManager(context_limit=200_000)

    def run_turn(self, user_message):
        self.conversation.add_user_message(user_message)
        for iteration in range(MAX_ITERATIONS):  # MAX_ITERATIONS = 50
            response = call_llm(self.conversation.messages, self.tools.schemas)
            if response.has_text_only:
                return response.text
            for tool_call in response.tool_calls:
                result = self.tools.execute(tool_call, self.workflow)
                self.conversation.add_tool_result(tool_call.id, result)

Expression Parser and Evaluator

Decision nodes contain conditions like Age >= 65 AND BMI < 30. These need to be parsed and evaluated at runtime. LEMON includes a custom expression parser that tokenizes condition strings, builds an Abstract Syntax Tree (AST), and evaluates the tree against a variable context [2].

The pipeline has three stages:

  1. Tokenization: The input string is scanned into tokens (IDENTIFIER, NUMBER, STRING, BOOL, comparators like GTE/LTE/EQ, logical operators AND/OR/NOT, parentheses).
  2. Parsing: A recursive descent parser builds an AST of BinaryOp, Variable, and Literal nodes.
  3. Evaluation: The evaluator walks the AST, resolves variable references from the execution context, and produces a boolean result.

Data

Evaluation Dataset

The evaluation framework uses benchmark workflows with known correct structures:

  • Diabetes Treatment Pathway: A clinical workflow for diabetes management decisions based on HbA1c levels, blood glucose, and patient age. Contains decision nodes with numeric thresholds, branching to different treatment recommendations (medication adjustment, specialist referral, hospital admission).
  • Liver Pathology Classification: A diagnostic workflow for classifying liver conditions based on lab results and imaging findings.

Each benchmark includes:

  • A natural language description of the workflow
  • A ground truth (golden) workflow with the correct node structure, connections, conditions, and outputs
  • A set of expected execution behaviors for known inputs

Experiments

Experiment Design

The evaluation harness runs each LLM model against each benchmark sample, potentially across multiple runs per configuration. For each run, the orchestrator attempts to build a workflow from the natural language description. The resulting workflow is then scored against the golden reference.

Scoring Framework

Scoring uses six dimensions, each producing a score between 0.0 and 1.0:

Dimension What It Measures How It's Calculated
Variables Input variable recall and type accuracy Fraction of golden variables found in extracted workflow, weighted by type match
Nodes Node count recall and type accuracy Fraction of golden nodes matched by type in extracted workflow
Topology Edge recall and label accuracy Fraction of golden edges matched (using node mapping), weighted by correct labels
Conditions Comparator and threshold accuracy For matched decision nodes, how accurately conditions reproduce the golden comparators and values
Outputs End node output similarity Text similarity between golden and extracted end node output values
Functional Execution routing agreement Fraction of test cases where both workflows reach the same end node given identical inputs

Functional Scoring

The functional dimension is distinct from the structural dimensions above. Rather than comparing the workflow structure, it compares behavior:

  1. Extract numeric thresholds from the golden workflow's decision conditions
  2. Generate boundary test cases: values below, at, and above each threshold
  3. Execute both the golden and extracted workflows with the same inputs
  4. Compare which end node each workflow reaches
  5. Score = fraction of test cases with matching routing

This catches cases where the workflow structure differs from the golden reference but the behavior is equivalent, as well as cases where the structure appears correct but conditions are subtly wrong.

Discussion

Where extraction fails:

  • Deeply nested branching: Workflows with many levels of conditional nesting are harder for the LLM to reconstruct accurately, particularly when branch paths reconverge.
  • Ambiguous condition phrasing: Natural language descriptions that use vague thresholds ("elevated", "abnormal") rather than numeric values lead to incorrect or missing conditions.
  • Complex compound conditions: Conditions combining multiple variables with mixed AND/OR logic are sometimes simplified or split incorrectly.
  • Implicit flow: When the source description omits explicit connections between steps, the orchestrator may create incorrect topology.

Suggestions for improvement:

  • Expand the evaluation dataset with more diverse clinical workflows
  • Add an iterative refinement pass where the orchestrator validates its own output and corrects errors
  • Improve prompt engineering to handle ambiguous descriptions more robustly
  • Explore few-shot prompting with example workflows

Conclusion

The evaluation framework provides a quantitative basis for measuring orchestrator quality. The six-dimension scoring approach captures both structural accuracy and behavioral correctness. Functional scoring is particularly valuable because it tests what matters most: whether the workflow produces the correct output for a given set of inputs, regardless of how the internal structure differs from the reference. This framework enables regression testing when prompts, tool schemas, or model versions change.
