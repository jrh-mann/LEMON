1. Logging In

Navigate to the application URL. Enter your email address and password, then click Login. New users can register by clicking the Register tab and providing an email, name, and password.

2. Creating a Workflow via Chat

Type a description of your workflow in the chat panel on the left side of the screen. For example: "Create a diabetes treatment workflow that checks HbA1c levels and recommends medication adjustments." The orchestrator will build nodes and connections on the canvas in real time. You can see each tool call as it executes.

3. Uploading a Flowchart Image

Click the Upload Files button on the home screen, or use the paperclip icon in the chat input. Select an image file (PNG, JPG) or PDF of a flowchart. The system will analyze the image and reconstruct it as an editable workflow on the canvas.

4. Editing on the Canvas

Drag nodes to reposition them. Right-click a node to open its context menu (edit, delete, connect). Draw connections by clicking the output port of one node and dragging to the input of another. Use scroll wheel to zoom and click-drag on empty space to pan.

5. Managing Variables

Open the right sidebar to view workflow variables. Each variable has a name, type (string, number, boolean, or enum), and optional description. Variables are used in decision conditions and calculation nodes. The orchestrator creates variables automatically, but you can also add or edit them manually.

6. Using Subworkflows

Create a subprocess node to reference another saved workflow. Configure the input mapping to connect parent variables to the child workflow's inputs. When executed, the subprocess runs the referenced workflow and returns its output as a derived variable.

7. Executing with Test Inputs

Click the Run Workflow button in the left sidebar. Enter values for each input variable in the dialog that appears. Click Run to start execution. The system steps through each node, highlighting the active node and the execution path on the canvas. The final output and execution context are displayed when complete.

8. Saving to Library

Click Save in the header to store your workflow in the personal library. You can access saved workflows later from the Library page. Each workflow stores its full state including nodes, edges, variables, and conversation history.

9. Publishing a Workflow

When saving a workflow, check the "Publish to Community Library" checkbox in the save dialog. This makes your workflow visible to other users in the Peer Review tab. Published workflows start as "unreviewed" and can be promoted to "reviewed" status through community voting.

10. Browsing and Voting on Public Workflows

In the Library page, switch to the Peer Review tab to browse all published workflows. Use the upvote and downvote buttons on each workflow card to vote on quality. The Published tab shows only workflows that have reached the vote threshold. Clicking on a published workflow lets you view its full structure.

11. Exporting

Navigate to the Export page. Choose your export format:

  • JSON: Complete workflow data including nodes, edges, variables, and metadata
  • Python: Compiled executable code that reproduces the workflow logic
  • PNG: Visual image of the workflow canvas

Deployment Manual

Prerequisites

  • Python 3.10 or later
  • Node.js 18 or later
  • uv (Python package manager): install with curl -LsSf https://astral.sh/uv/install.sh | sh
  • An Anthropic API key (obtain from console.anthropic.com)

Local Development Setup

  1. Clone the repository:

    git clone https://github.com/jrh-mann/LEMON.git
cd LEMON

  2. Install Python dependencies:

    uv sync

  3. Install frontend dependencies:

    cd src/frontend
npm install
cd ../..

  4. Configure environment variables:

    cp .env.example .env

    Then edit .env and add your Anthropic API key:

    ANTHROPIC_API_KEY=sk-ant-...
ANTHROPIC_MODEL=claude-opus-4-6

  5. Start the development servers:

    ./scripts/dev.sh

  6. Access the application:

    • Frontend: http://localhost:5173
    • Backend: http://localhost:5001
    • Logs: /tmp/lemon-backend.log, /tmp/lemon-frontend.log

Azure Deployment

The project uses GitHub Actions for production deployment. The workflow file is at .github/workflows/deploy-prod.yml.

Deployment process:

  1. Push code to the prod branch
  2. GitHub Actions automatically triggers the deployment workflow
  3. The workflow installs Node.js 20, builds the frontend (npm ci && npm run build)
  4. Packages the backend (src/backend, compiled frontend, scripts, configuration) into a ZIP archive
  5. Deploys to Azure Web App using the publish profile stored as a GitHub secret

To configure deployment for a new environment:

  • Set up an Azure Web App instance
  • Add the Azure publish profile as a GitHub repository secret named AZURE_WEBAPP_PUBLISH_PROFILE
  • Push to the prod branch to trigger deployment

GDPR and Data Privacy

Scope

LEMON is a workflow authoring tool developed as a university research project. It is not a clinical system and does not process, store, or have access to patient health records, NHS systems, or electronic health record databases. All workflows describe clinical decision logic in abstract terms (e.g. "if HbA1c > 48, start metformin") and do not reference individual patients.

Personal data collected

The system collects the following personal data from registered users:

  • Email address and display name, for authentication and identification within the application.
  • Password, stored as a PBKDF2-SHA256 hash with a per-user random salt (390,000 iterations). Plaintext passwords are not stored or logged.
  • Session tokens, stored as SHA-256 hashes in the database. Raw tokens are held only in the user's browser cookie.

No special category data (as defined under Article 9 of the UK GDPR) is collected by the system itself. The system does not request or require any health data, demographic data, or other sensitive personal information from its users.

User-generated content

Users create workflows and interact with the system through a chat interface. The content of these interactions, including chat messages, uploaded images, and workflow definitions, is stored in SQLite databases on the server. Conversation logs are retained as an audit trail of LLM interactions.

Users are responsible for the content they input. If a user were to enter patient-identifiable information into the chat or upload documents containing personal health data, that content would be stored in the conversation log and transmitted to the Anthropic API (see below). The system does not prompt for, require, or validate whether user input contains personal data. Users must not enter real patient data.

Third-party data processing

LEMON uses the Anthropic Claude API to power its conversational workflow builder. When a user sends a message, the system transmits the conversation history and any attached files to Anthropic's servers for processing. This data is sent over HTTPS. No content filtering or redaction is applied prior to transmission. Anthropic's own data use and retention policies govern the handling of this data once received.

No other third-party services are used. The system does not include analytics, advertising, tracking, or content delivery network integrations.

Data storage and security

All application data is held in SQLite databases and flat files within the server's local filesystem. In the production deployment on Azure, this storage resides within the Azure Web App instance.

Security measures in place:

  • HTTPS for all client-server communication in production.
  • Content-Security-Policy, X-Frame-Options (DENY), X-Content-Type-Options (nosniff), and strict Referrer-Policy headers on all responses.
  • API rate limiting at 60 requests per minute per IP address.
  • Login brute-force protection: 8 failed attempts per IP and email combination triggers a 10-minute lockout.
  • User ownership enforcement on all API endpoints. Users may only access their own workflows and data. Published workflows are visible to other authenticated users on a read-only basis.

Databases and uploaded files are not encrypted at rest. In any deployment handling sensitive data, disk-level encryption or an encrypted database layer such as SQLCipher would be required.

Data retention

User sessions expire after 12 hours (or 14 days if "remember me" is selected). Expired sessions are purged automatically. A maximum of 5 concurrent sessions per user is enforced.

Workflow data and conversation logs are retained indefinitely unless manually deleted by the user. Users may delete individual workflows through the application interface. There is no automatic retention period or scheduled purge for conversation logs or uploaded files.

Rights of data subjects

Under the UK GDPR, data subjects have the right to access, rectify, and erase their personal data, and the right to data portability. The current system supports deletion of individual workflows but does not provide a self-service account deletion facility or a bulk data export function. These would need to be implemented prior to any production deployment to meet the requirements of Articles 15 through 20 of the UK GDPR.

Clinical deployment considerations

LEMON in its current form is a research prototype. Before deployment in any clinical or NHS setting, the following would be required:

  • A Data Protection Impact Assessment (DPIA) under Article 35 of the UK GDPR.
  • A Data Processing Agreement (DPA) with Anthropic covering the processing of any data transmitted to their API.
  • Explicit user consent mechanisms for data collection, storage, and third-party transmission.
  • Implementation of data retention limits and automated purge schedules.
  • Account deletion and data export endpoints to support data subject rights.
  • Encryption of data at rest.
  • Compliance review against the NHS Data Security and Protection Toolkit (DSPT).
